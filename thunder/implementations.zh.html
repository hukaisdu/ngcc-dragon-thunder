Thunder 杂凑家族

实现提交包结构、构建与 KAT、核对注记

提交包内有 X86 与 ARM 两套树，各分 Reference / Additional / Optimized 三种实现； ngcc.dev 构建与计时用 Thunder-X86 的 Reference（XOF 以定长 1280/1152/1024 bit 构建）。 make -C hash-33 test 复现 KAT（6/6 PASS）。源码注释为 GB 编码中文。 ngcc.dev 的核对结论：未发现参数或常数不吻合；各输出长度之间的 domain separation 经三条独立机制确认。

提交包结构（官方 Thunder.zip，解包于 harness/hash-33/Thunder/）

Thunder/Implementations and Test_vector/
├── Thunder-X86/Implementations/       # <- ngcc.dev 构建并计时（"X86" 为大写）
│   ├── Reference_Implementation/      # 六个实例: Thunder-512/768/1024, Thunder-XOF-256/384/512
│   ├── Additional_Implementation/{Thunder-512, Thunder-768, Thunder-1024}
│   └── Optimized_Implementation/{Thunder-512, Thunder-768, Thunder-1024}
└── Thunder-ARM/Implementations/       # 与 Thunder-X86 同构

每个实例目录含 CryptHash_AlgorithmInstance.{c,h} 与 KAT 驱动。 定长三实例共用一份逐字节相同的 .c；XOF 三实例共用另一份，只多了多块 squeeze 循环。

构建与 KAT

前置需求：GCC（≥9）与 CMake。在本仓库的 harness/ 目录下：

cd harness
make -C hash-33          # 构建六个实例库（reference）
make -C hash-33 test     # 跑 KAT harness; 汇总在 results/

预期输出：六个实例对提交的 test vector（KAT = Known-Answer Test，已知答案测试）全部 KAT-PASS（清单 kat.sha256，24 个文件）， 每次计时前先做 KAT 检查（x86_1，2026-09-25 → 09-28）。

核对注记（ngcc.dev 源码审查）

未发现 spec 与实现之间任何参数或常数不吻合。整个置换都被核对过（不是抽样）： RC[12]、25 个 lane rotation τ(x,y)、θ 的偏移（t = 41/50/6/10/27、u = 26、r = 1、s = 36）、 π 的 lane 置换、3 次的 ψ、轮序 ι → ρ → θ → π → ψ、六个实例的 capacity/rate、IV 加载 （数组逆序存放、加载补偿，lane j 收到 spec 的 IV_j——六个实例全部核对）、前馈、消息布局、 padding 与 final-block 常数。细节见 pseudocode.md。

  • 外观小问题：头文件注释 “IV[0] is the least significant lane” 是错的——数组按 spec 指标降序存放；但最终放置正确。
  • XOF 实例没有指定的 digest 长度；NGCC wrapper 将 DIGEST_BIT_LENGTH 固定为一个 squeeze block（1280/1152/1024 bit），因此元数据报告 160/144/128 字节。
