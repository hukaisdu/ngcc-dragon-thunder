分析第三方状态、constant-time 审查、核对注记

截至 ngcc.dev 2026-10-28 快照，Thunder 没有已公开的 vulnerability finding （ngcc.dev security 报告）。这只是公开 finding 清单的当前状态，不是安全性背书；该候选仍在评审中。

Constant-time 审查（ngcc.dev）

范围：归档的 reference 实现、固定 digest 参数与固定消息长度；消息内容与中间状态视为秘密。 审查了两个源码点：

  • Reference 入口：Thunder-ARM/…/Reference_Implementation/Thunder-1024/CryptHash_AlgorithmInstance.c:175。
  • XOF 输出位拷贝中的 if (src_bit) （Thunder-X86/…/Thunder-XOF-256/CryptHash_AlgorithmInstance.c:187）。GCC -O2 将其编译为地址固定的 cmovne，因此在受检构建中不构成机器分支——其他编译器与目标平台仍需检查。

结论：受检 GCC 构建未升级为问题。全文： 镜像审查页 · 线上。

实现与规范核对

未发现参数或常数不吻合。整个置换逐项核对（非抽样）；capacity、rate、IV 放置 （数组逆序 + 加载补偿）、前馈、消息布局、padding 与 final-block 常数均与 spec 一致。

输出长度 domain separation

共享 capacity 的实例对（如 Thunder-512 / Thunder-XOF-256，均为 c = 576）之间， 仅靠不同的 IV（spec IV 表）实现分离——六个实例加载的 IV lane 集合完全不同（ngcc.dev 已验证）。 rate/capacity 划分（576/832/1088）区分安全等级但区分不了这些配对。 final-block 常数 C = 0^{c−1}‖1 在六个实例中完全相同；它分离的是末块与非末块 （防长度扩展），对实例间分离没有贡献。

XOF 固有的注意点：同一 XOF 实例内，不同长度的输出互为前缀；harness 暴露的三个固定长度 （1280/1152/1024 bit）不是三个独立的 hash 函数。

值得记住的几点

  • IV 常数（spec 的 IV 表）没有给出导出规则——已在生效 LaTeX 源中全文确认；这是一个值得注意的 透明度缺口，不是 break。对比：Dragon 的 IV 有明文的 SM3 counter-mode 导出程序。
  • ψ 的代数次数为 3（Keccak 的 χ 为 2），θ 使用双列校验——做 trail / differential 搜索时相关。
  • 相关文献：“Chinese NGCC Algorithms: The First Week of AI Cryptanalysis”， IACR ePrint 2026/2266——覆盖全部 119 个 NGCC Round-1 候选的首周 AI 辅助分析综述（191 项公开 finding，78 项 Critical）；文中对 Thunder 未报告 finding， 与 ngcc.dev 公开清单一致。
