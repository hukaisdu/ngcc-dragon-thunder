实现提交包结构、构建与 KAT、核对注记

提交包内有 x86 与 ARM 两套树，各分 Reference / Additional / Optimized 三种实现； ngcc.dev 构建与计时用的是 Dragon-x86 的 Reference（XOF 以定长 1280/1152/1024 bit 构建）。 在 harness 根目录执行 make -C hash-07 test 可复现 KAT（6/6 PASS）。 ngcc.dev 的源码核对结论：未发现与规范的偏差；两条使用注意事项见下文。

提交包结构（官方 Dragon.zip，解包于 harness/hash-07/Dragon/）

Dragon/Implementations and Test_vector/
├── Dragon-x86/Implementations/
│   ├── Reference_Implementation/      # <- ngcc.dev 构建并计时
│   │   ├── Dragon-512/  Dragon-768/  Dragon-1024/
│   │   └── Dragon-XOF-256/  Dragon-XOF-384/  Dragon-XOF-512/
│   ├── Additional_Implementation/{Dragon-512, Dragon-768, Dragon-1024}
│   └── Optimized_Implementation/{Dragon-512, Dragon-768, Dragon-1024}
├── Dragon-ARM/Implementations/        # 与 Dragon-x86 同构
└── (Test_Vector/ 与 Others/ 自评估树, 见提交包)

每个实例目录含 CryptHash_AlgorithmInstance.{c,h}、KAT 驱动 （KAT_CryptHash.c）与 ICCS 辅助（drng.c/h）。定长实例共用一份 191 行的 .c；三个 XOF 共用另一份 245 行的变体（带真正的多块 squeeze 循环）。 全部实例参数都放在头文件里。

构建与 KAT

前置需求：GCC（≥9）与 CMake。在本仓库的 harness/ 目录下：

cd harness
make -C hash-07          # 构建六个实例库（reference）
make -C hash-07 test     # 跑 KAT harness; 汇总在 results/

预期输出：六个实例对提交的 test vector（KAT = Known-Answer Test，已知答案测试）全部 KAT-PASS（清单 kat.sha256，24 个文件）， 每次计时前先做 KAT 检查（x86_1，2026-09-25 → 09-28）。

核对注记（ngcc.dev 源码审查）

未发现 hash-07 与规范之间的偏差。参数常数、轮常数、rotation offsets、lane 映射、padding、 domain separation 规则、前馈与 digest 顺序全部一致（细节见 pseudocode.md 的 "Implementation vs specification"）。

  • 定长实例的 CryptHash() 完全忽略 digest_len_bits：总是写入 DIGEST_LANE_NUM 个 lane 并返回 0。传入更小的值会缓冲区溢出；更大的值会被静默截断。
  • ROTL64(x, 0) 按标准是未定义行为，但没有任何 rotation 常数为 0，因此不可达。
  • IV 在头文件中按 spec 逆序存放；加载代码做了补偿，每个 lane 收到的都是 spec 的 IV_j （两张 9-lane 表逐项核对过；spec 的 SM3 counter 导出程序未被重新计算）。
  • 部分字节输入处理正确（padding 前先屏蔽超出 msg_len_bits 的位）。
